# Contract: iCal Feed HTTP Endpoint

**Feature**: 001-ical-turnover-export
**Date**: 2026-03-16
**Type**: HTTP endpoint (read-only)

## Endpoint

```text
GET /api/turnovercal/{token}/calendar.ics
```

**Authentication**: None (requires_auth = False). Access is controlled
by the secret `{token}` path segment. The token is a URL-safe
base64-encoded string generated by `secrets.token_urlsafe(32)`.

**Content-Type**: `text/calendar; charset=utf-8`

## Request

### Path Parameters

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| token | string | Yes | Secret URL token (43-char base64) |

### Headers

No special headers required. Standard HTTP/1.1 headers accepted.
Calendar clients typically send `Accept: text/calendar` but this is
not required.

### Query Parameters

None.

## Response

### 200 OK — Valid Calendar

Returned when the token is valid. The body is a complete RFC 5545
iCalendar document.

**Headers**:

```text
Content-Type: text/calendar; charset=utf-8
```

**Body** (example):

```text
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Home Assistant//TurnoverCal//EN
CALSCALE:GREGORIAN
METHOD:PUBLISH
X-WR-CALNAME:Turnover - Beach House
X-WR-TIMEZONE:America/New_York
BEGIN:VTIMEZONE
TZID:America/New_York
BEGIN:STANDARD
DTSTART:20261101T020000
RRULE:FREQ=YEARLY;BYMONTH=11;BYDAY=1SU
TZOFFSETFROM:-0400
TZOFFSETTO:-0500
TZNAME:EST
END:STANDARD
BEGIN:DAYLIGHT
DTSTART:20260308T020000
RRULE:FREQ=YEARLY;BYMONTH=3;BYDAY=2SU
TZOFFSETFROM:-0500
TZOFFSETTO:-0400
TZNAME:EDT
END:DAYLIGHT
END:VTIMEZONE
BEGIN:VEVENT
UID:a1b2c3d4e5f60718@turnovercal.homeassistant
DTSTAMP:20260316T120000Z
DTSTART;TZID=America/New_York:20260310T110000
DTEND;TZID=America/New_York:20260310T150000
SUMMARY:Turnover - Beach House
DESCRIPTION:Cleaning window between guests
STATUS:CONFIRMED
END:VEVENT
END:VCALENDAR
```

**VCALENDAR properties** (always present):

| Property | Value | Notes |
| --- | --- | --- |
| VERSION | 2.0 | RFC 5545 required |
| PRODID | -//Home Assistant//TurnoverCal//EN | Identifies producer |
| CALSCALE | GREGORIAN | RFC 5545 default |
| METHOD | PUBLISH | Read-only feed |
| X-WR-CALNAME | `{prefix} - {property_name}` | Calendar display name |
| X-WR-TIMEZONE | `{timezone}` | Hint for clients without VTIMEZONE support |

**VEVENT properties** (per turnover event):

<!-- markdownlint-disable MD013 -->

| Property | Type | Description |
| --- | --- | --- |
| UID | text | Truncated SHA-256 hex digest (16 chars); `{hex16}@turnovercal.homeassistant` |
| DTSTAMP | UTC datetime | When the event was last generated/modified |
| DTSTART | local datetime + TZID | Turnover window start (checkout time) |
| DTEND | local datetime + TZID | Window end (next check-in or lock-adjusted) |
| SUMMARY | text | `"{prefix} - {property_name}"`; no guest PII |
| DESCRIPTION | text | `"Cleaning window between guests"` |
| STATUS | text | `CONFIRMED` for all events |

<!-- markdownlint-enable MD013 -->

**VTIMEZONE**: Automatically generated for the HA-configured local
timezone. Always present when VEVENT datetimes use TZID parameter.

### 200 OK — Empty Calendar

Returned when the token is valid but no turnover events exist. The
body is a valid VCALENDAR with no VEVENT components.

```text
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Home Assistant//TurnoverCal//EN
CALSCALE:GREGORIAN
METHOD:PUBLISH
X-WR-CALNAME:Turnover - Beach House
X-WR-TIMEZONE:America/New_York
END:VCALENDAR
```

### 401 Unauthorized

Returned when the token is invalid or missing.

**Body**: Empty (no information leakage).

```text
HTTP/1.1 401 Unauthorized
```

### 401 Unauthorized (removed entry)

If the config entry associated with the token has been removed
(integration unloaded), the endpoint also returns 401. From the
client's perspective, the token no longer resolves to an active
instance and is indistinguishable from an invalid token — this
avoids leaking whether a token was ever valid.

**Body**: Empty.

## Event Lifecycle in Feed

<!-- markdownlint-disable MD013 -->

| Scenario | DTSTART | DTEND | Duration |
| --- | --- | --- | --- |
| Normal turnover (4-hour gap) | Checkout time | Check-in time | 4 hours |
| Multi-day turnover | Checkout time | Check-in time | N days |
| Zero-gap (back-to-back) | Checkout time | Checkout + 1 min | 1 minute |
| Trailing (no next guest) | Checkout time | Checkout + trailing duration | Default 4 hours |
| Early unlock (grace period) | Unlock time (moved earlier) | Check-in time or lock-adjusted | Varies |
| Lock-adjusted (multi-day) | Checkout time | 00:00 day after unlock | Varies |
| Lock-adjusted (same-day check-in) | Checkout time | Check-in time (unchanged) | Unchanged |

<!-- markdownlint-enable MD013 -->

## UID Stability Contract

The UID for a turnover event MUST remain stable across:

- Recalculations due to source event time changes
- Keymaster DTEND adjustments
- HA restarts
- Cache load/save cycles

The UID is derived from the pair of source guest event identifiers
using a one-way SHA-256 hash. Calendar clients use UID to deduplicate
events; instability would cause duplicate entries.

### Source Identifier Strategy

When the upstream calendar integration populates
`CalendarEvent.uid` (the iCal UID from the source calendar), the
source identifier is derived from that UID. This provides true
stability across event time changes because the iCal UID is
assigned by the booking platform and does not change when a
reservation is modified.

When `CalendarEvent.uid` is not available (i.e. `None`), the
source identifier falls back to a content hash of the event
summary and normalized start/end times. In this fallback mode,
UIDs will change if the source event times change.

**Dependency**: Full UID stability requires the upstream calendar
integration (Rental Control) to expose `CalendarEvent.uid`. See
[homeassistant-rental-control#409](
https://github.com/tykeal/homeassistant-rental-control/issues/409
).

## Rate Limiting

No explicit rate limiting is applied. The endpoint serves pre-computed
cached data and imposes negligible load on HA. Calendar clients
typically poll every 15–60 minutes.

## Compatibility

Tested consumer targets (SC-003):

- Google Calendar (iCal subscription URL)
- Apple Calendar / iCloud Calendar
- Microsoft Outlook (Internet Calendar subscription)

All three require:

- Valid VCALENDAR with VERSION 2.0
- VTIMEZONE for non-UTC datetimes
- Stable UIDs for change detection
- `text/calendar` Content-Type
